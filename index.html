01

An AI agent that triages every request sent to operations

Pre-launch TypeScriptClaude APICloudflare WorkersDurable ObjectsSlackAirtable

Problem

Requests reached ops through two busy Slack channels. A Zap copied every post into the task list, so work that was already done or already open came in again.

What I built

A Slack bot that becomes the only poster in both channels. People message it directly, and a Claude agent checks the request against the live task list. It decides whether the request is already done, already open, an escalation, a new project or not for ops, then posts and records it.

Result

27 unit tests pass, including tests that protect the post format the team's Airtable formulas read. A test mode posts to private channels and writes nothing, so it can be trialled safely before launch.

02

A call-recording pipeline that feeds an AI review agent

Live Google Apps ScriptGoogle Drive APIAirtable APIAI agents

Problem

An AI agent was meant to review every onboarding call. But recordings reach Google Drive hours or days after the call, with nothing tying them to it, so the agent had nothing to work on.

What I built

An Apps Script job that runs every 10 minutes. It matches each new recording to its call, writes the link back to the call record, and creates a review task with everything the agent needs to find the call, the recording and its checklist.

Result

The first version matched on nearest time and linked 22 of 40 backfilled calls to the wrong recording. Requiring the guest's name in the file title fixed it, and anything unmatched is now logged for a person rather than guessed. The full chain was tested end to end: transcript, checklist review and score.

03

Escalation tracking inside Slack, with SLA clocks

Built ZapierSlackAirtableForms

Problem

Client escalations were raised in Slack threads with no clear owner, no response clock and no record of how each one was closed.

What I built

Case management that stays in Slack. A reaction or form opens a case and posts a case card, an emoji claims it, and a close form records the root cause. Airtable tracks owner, status and response time in business hours. It alerts when a case passes 48 hours and flags churn words in the client's own message.

Result

Seven Zaps and one Airtable base turn loose threads into tracked cases. Every case now has an owner, a timestamped history and a reason it closed.

04

A weekly health index for 1,250 client agencies

Rolling out Airtable automationsAirtable scriptingFormulas

Problem

A weekly job records a health score for every agency. The team read the history rows as duplicates, cancelled agencies still showed up, and the table grew by 1,250 rows every week.

What I built

I added each agency's real account status from the source of truth, so the team's view shows only active agencies, with 130 cancelled or paused ones hidden. Then I redesigned storage: one live row per agency updated in place, a monthly snapshot kept for four months, and 30-, 60- and 90-day trend fields.

Result

The table stays at about 5–6k rows instead of growing forever, and the team gets trends instead of duplicate-looking rows. Before rollout, I simulated the new logic on 33 weeks of real data.

05

Bringing a production AI platform back, then giving it backups

Ongoing LinuxSSHMySQL / TiDBBash

Problem

An internal AI operations platform went down after a hosting plan change rotated its database password. The database had no backup anywhere.

What I built

I restored service by passing the new credential straight to the server over SSH, never printing it or writing it to disk, then redeployed the recorded release. Next I started moving the 84-table, 2.26-million-row database to a self-hosted one with nightly backups.

Result

The migration rehearsal caught a table with no primary key, which would have broken the restore. I fixed it at the source before cutover, not in the copy.
